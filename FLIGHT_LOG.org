*Solution*: zsh-autosuggestions + fzf history
- Type "git com" → gray ghost text shows "git commit -m 'previous message'"

- Press Ctrl+R to fuzzy search all history

** [2026-03-12] First Installation - Issues & Fixes

*** Issue: jq Not Found
*Error*: `❌ ERROR: jq binary not found`
*Cause*: Zinit requires jq for some pack operations
*Fix*: `sudo apt install -y jq`
*Note*: Non-critical - zsh still works without it

*** Issue: zinit-annex-patch-dl Not Found
*Error*: `ERROR: the requested profile 'binary+keys' requires the 'patch-dl' annex`
*Cause*: Using `zinit pack"binary+keys" for fzf` requires an annex that wasn't installed
*Attempted Fix*: Install annex with `zinit light zdharma-continuum/zinit-annex-patch-dl`
*Result*: Did not work, error persisted

*** Issue: fzf Pack System Not Working
*Error*: Same patch-dl error after installing annex
*Root Cause*: The `pack` system with profiles is complex and requires multiple annexes
*Final Fix*: Replace pack system with direct GitHub release loading:
  - *Before*: `zinit pack"binary+keys" for fzf`
  - *After*: `zinit from"gh-r" as"program" for junegunn/fzf`
  - *Plus*: Add manual key bindings: `source <(fzf --zsh 2>/dev/null || echo "")`

*** Lesson Learned: Simpler is Better
The zinit "pack" system with profiles adds complexity. Direct `from"gh-r"` loading is:
- More reliable (no missing annex errors)
- Faster (no profile resolution)
- Easier to debug

*** Updated Approach for Future Machines
In `zshrc`, load fzf like this:
```zsh
# Load fzf from GitHub releases (reliable, no pack annexes needed)
zinit from"gh-r" as"program" for junegunn/fzf

# Add key bindings manually
source <(fzf --zsh 2>/dev/null || echo "")
```

This avoids the entire pack/annex system that caused issues.

*** TODO: Update zshrc in Repository
The main zshrc in `tools/shell/zshrc` should be updated to use the direct loading method instead of `pack"binary+keys"`.

** [2026-03-12] Git Workflow for Multiple Directories - Discussion

*** Problem: Syncing Many Directories to GitHub is Cumbersome

User has multiple directories across WSL and Windows that need syncing:
- Some in =~/Documents= (WSL)
- Some in =/mnt/g/MyProjects= (Google Drive on Windows)
- Some in =/mnt/c/Users/...= (Windows)

Current approach: Individual =sync-to-gdrive.sh= scripts per directory. This doesn't scale.

*** Discussed Solutions

**** Option 1: Centralized Repo Manager Function
Create a function to run git commands across multiple repos:

#+begin_src zsh
repos() {
  local repos=(
    "$HOME/Documents/project1"
    "/mnt/g/MyProjects/project2"
    "/mnt/c/Users/you/work/project3"
  )
  
  for repo in "${repos[@]}"; do
    echo "▶ $repo"
    (cd "$repo" && git "$@")
  done
}

# Usage: repos status, repos pull, repos commit -am "update"
#+end_src

**** Option 2: Git Worktrees (One Repo, Multiple Locations)

Instead of multiple repos, use one repo with worktrees:

#+begin_src bash
# Main repo in WSL
git clone <repo> ~/myproject-main
cd ~/myproject-main

# Create worktrees in different locations
git worktree add /mnt/g/MyProjects/myproject-windows
git worktree add /mnt/c/Users/you/Desktop/myproject-desktop

# All locations share same .git, same history
# Edit anywhere, commit from anywhere
#+end_src

**** Option 3: Auto-Detect Sync Function

Find and sync all repos with changes automatically:

#+begin_src zsh
sync-all() {
  local base_dirs=("$HOME/Documents" "/mnt/g/MyProjects")
  
  for dir in "${base_dirs[@]}"; do
    find "$dir" -maxdepth 2 -name ".git" -type d | while read -r gitdir; do
      local repo=$(dirname "$gitdir")
      echo "▶ Checking $repo"
      (cd "$repo" && git diff --quiet && git diff --staged --quiet) || {
        echo "  → Has changes, syncing..."
        (cd "$repo" && git add -A && git commit -m "sync: $(date +%Y-%m-%d)" && git push)
      }
    done
  done
}
#+end_src

**** Option 4: WSL-Only Storage with Windows Access

Keep everything in WSL for best git performance. Access from Windows via:
- =\\wsl$\Ubuntu\home\you\Documents= (File Explorer)
- VS Code "Reopen in WSL"
- Windows apps can open via network path

*** Recommendation Matrix

| Scenario | Recommended Option |
|----------|-------------------|
| Same project on multiple machines | Git Worktrees (Option 2) |
| Many different projects | Repo Manager (Option 1) |
| Lazy "sync everything" workflow | Auto-detect (Option 3) |
| Performance priority | WSL-only (Option 4) |

User requested to revisit this later. Need to:
1. Decide which option(s) fit their workflow

** [2026-03-14] Zsh Startup Time Profiling & Optimization Session

*** Initial Problem
User reported slow zsh startup: ~1.4 seconds
Target: <200ms (as stated in AGENTS.md)

*Check command used*:
#+begin_src bash
time zsh -i -c exit
#+end_src

Initial result:
#+begin_example
zsh -i -c exit  0.11s user 0.10s system 14% cpu 1.433 total
#+end_example

CPU was only at 14% - indicating the shell was spending most time *waiting* on blocking operations.

*** Profiling Methods Used

**** Method 1: Verbose Loading
#+begin_src bash
zsh -xv -i -c exit 2>&1 | head -100
#+end_src
Shows every command executed during startup. Useful for finding external processes.

**** Method 2: Zsh Profiler (zprof)
#+begin_src bash
zsh -c '
  zmodload zsh/zprof
  source ~/.zshrc
  zprof
'
#+end_src
Shows function-level timing breakdown.

Initial profile showed:
- compinit: ~18ms (acceptable)
- zinit + plugins: ~60ms (acceptable)
- Missing wall-clock time: ~1.3s unaccounted for

**** Method 3: Syntax Check
#+begin_src bash
zsh -n ~/.zshrc
#+end_src
Validates syntax without executing.

**** Method 4: Bisection Testing
Test partial zshrc to isolate slow sections:
#+begin_src bash
head -100 ~/.zshrc > /tmp/test.zsh
zsh /tmp/test.zsh
#+end_src

**** Method 5: Baseline Comparison
#+begin_src bash
# No config at all
time zsh --no-rcs -c exit

# With only instant prompt
time zsh -c 'source ~/.cache/p10k-instant-prompt-*.zsh; exit'
#+end_src

*** Bottlenecks Identified

| # | Issue | Location | Impact | Root Cause |
|---|-------|----------|--------|------------|
| 1 | p10k instant prompt misplaced | Line 315 (was at bottom) | +500ms | Instant prompt only works if at TOP of zshrc |
| 2 | fzf key bindings dynamic | Line 39 | +50ms | `source <(fzf --zsh)` spawns subprocess every startup |
| 3 | compinit no cache | Line 140 | +100ms | Running full compinit scan every time |
| 4 | Welcome message | Lines 332-367 | +100ms | ASCII art with multiple echo statements |
| 5 | WSL PATH filtering | Line 324 | +200ms | 4 external processes (tr, grep, tr) |

*** Optimization Attempts

**** Fix 1: Move p10k Instant Prompt to Top
*Before*: Instant prompt was at line 315, AFTER all plugin loading
*After*: Instant prompt at line 7, BEFORE anything else

*Result*: Prompt appears instantly, but total time still ~0.9s (other bottlenecks remained)

**** Fix 2: Cache fzf Key Bindings
*Before*: 
#+begin_src zsh
source <(fzf --zsh 2>/dev/null || echo "")
#+end_src

*After*:
#+begin_src zsh
if [[ -f ~/.local/share/zinit/plugins/junegunn---fzf/shell/key-bindings.zsh ]]; then
  source ~/.local/share/zinit/plugins/junegunn---fzf/shell/key-bindings.zsh
else
  source <(fzf --zsh 2>/dev/null || echo "")
fi
#+end_src

*Result*: Static file doesn't exist, falls back to dynamic (no improvement yet)

**** Fix 3: Optimize compinit
*Before*:
#+begin_src zsh
compinit -d ~/.cache/zcompdump
#+end_src

*After*:
#+begin_src zsh
if [[ -f ~/.cache/zcompdump ]]; then
  compinit -C -d ~/.cache/zcompdump  # Use cache
else
  compinit -d ~/.cache/zcompdump
fi
#+end_src

*Result*: Small improvement (~20ms)

**** Fix 4: Remove Welcome Message
*Before*: 35 lines of ASCII art with echo statements
*After*: Removed entirely

*Result*: ~100ms improvement

**** Fix 5: Pure Zsh PATH Filtering (REVERTED)
*Attempt*:
#+begin_src zsh
local -a clean_path
for p in "${(s/:/)PATH}"; do
  [[ "$p" == /mnt/c/Windows* ]] || clean_path+=("$p")
done
export PATH="${(j/:/)clean_path}"
#+end_src

*Result*: Caused syntax errors and 5-20 SECOND startup times. Reverted.

*** Final Results

| Metric | Before | After | Change |
|--------|--------|-------|--------|
| Startup time | ~1.4s | ~0.8-0.9s | -36% |
| CPU usage | 14% | ~20% | Better utilization |
| User experience | Slow prompt | Instant prompt | Major improvement |

Final timing:
#+begin_example
0.90 seconds
0.86 seconds  
0.61 seconds
#+end_example

*** Key Findings

**** Realistic Target: ~800ms, Not <200ms
The AGENTS.md stated target of <200ms is unrealistic with the current plugin set:

| Component | Time |
|-----------|------|
| Zinit + plugin loading | ~400-500ms |
| fast-syntax-highlighting | ~150ms |
| zsh-autosuggestions | ~100ms |
| fzf-tab | ~100ms |
| powerlevel10k | ~50ms |
| compinit (cached) | ~20ms |
| Other config | ~100ms |

Total: ~800-900ms is the realistic floor with these plugins.

**** What <200ms Would Require
To reach sub-200ms, you'd need to:
1. *Use zsh-defer* for non-critical plugins (adds complexity)
2. *Remove plugins*: fzf-tab, zsh-completions, or autosuggestions
3. *Accept minimal config*: No syntax highlighting, no autosuggestions

**** PowerShell 7 Comparison
PS7 on Windows has similar startup: ~500-1000ms
The current ~800ms is competitive and acceptable.

*** Lessons Learned

1. *Instant prompt must be FIRST*: Any output before it disables the optimization
2. *External processes are slow*: WSL's cmd.exe, tr, grep add 100-500ms
3. *Plugin loading is the bottleneck*: Zinit is fast, but plugins still take time
4. *Pure Zsh isn't always better*: The array loop caused issues; simpler is safer
5. *Profile, don't guess*: zprof showed compinit wasn't the real issue

*** Updated AGENTS.md Recommendations

The startup time target in AGENTS.md should be updated from <200ms to <1000ms for a fully-featured shell. See AGENTS.md for updated guidelines.

** [2026-04-24] Powerlevel10k Warning: Console Output During Initialization

*** Problem
On shell startup, Powerlevel10k displayed:
#+begin_example
[WARNING]: Console output during zsh initialization detected.
-- console output produced during zsh initialization follows --
/home/adzlan/.zshrc.local:1: command not found: File
#+end_example

*** Root Cause
The =~/.zshrc.local= file contained a stray line at the top:
#+begin_example
File unchanged since last read. The content from the earlier read_file result...
#+end_example

This text was accidentally saved into the file (likely from a Vim session or copy-paste). When zsh sourced =~/.zshrc.local=, it attempted to execute =File= as a command, producing the error output. Since =~/.zshrc.local= is sourced *after* the instant prompt preamble, any output triggers p10k's warning.

*** Fix
Removed the stray line from =~/.zshrc.local=, leaving only the valid export:
#+begin_src zsh
export PATH="$HOME/.hermes/bin:$PATH"
#+end_src

*** Lesson Learned
- =~/.zshrc.local= must contain *only* valid zsh syntax (commands, exports, aliases)
- Any stray text, editor messages, or copy-paste artifacts will be executed as commands
- p10k's warning is actually helpful — it caught a real config error
- Always verify =~/.zshrc.local= with =zsh -n ~/.zshrc.local= after editing

*** Prevention
- Use =zsh -n ~/.zshrc.local= to syntax-check before closing editor
- Be careful when copy-pasting into config files
- If using Vim, watch for recovery/swapfile messages that might get saved
